# EXPLORING THE WHEN CONDITION WITH ANSIBLE


## Resources Summary



## Lab Objective
In this lab, we’ll explore the when condition, a key tool in Ansible that lets you control task execution based on logical expressions. Using when, you can write smarter playbooks that adapt to dynamic conditions, prevent unnecessary actions, and avoid errors.

Why Conditions Matter
Conditions ensure your tasks are executed only when required, making your playbooks more efficient and robust. While you won’t use every operator available, understanding the options makes your playbooks flexible enough to handle diverse scenarios. Here’s a handy table of operators for reference:




| Term | Description | Example Usage with `when:` |
|------|-------------|---------------------------|
| `==` | Equal to comparison. Checks if two values are the same. | `when: ansible_os_family == "Debian"` |
| `!=` | Not equal to comparison. Checks if two values are different. | `when: ansible_distribution != "Ubuntu"` |
| `<` | Less than comparison. Checks if a value is less than another. | `when: ansible_distribution_version < "20.04"` |
| `<=` | Less than or equal to comparison. | `when: ansible_distribution_version <= "20.04"` |
| `>` | Greater than comparison. Checks if a value is greater than another. | `when: ansible_distribution_version > "18.04"` |
| `>=` | Greater than or equal to comparison. | `when: ansible_distribution_version >= "18.04"` |
| `and` | Logical AND. All conditions must be true. | `when: ansible_os_family == "Debian" and ansible_distribution_version >= "20.04"` |
| `or` | Logical OR. At least one condition must be true. | `when: ansible_os_family == "Debian" or ansible_os_family == "RedHat"` |
| `not` | Logical NOT. Reverses the result of a condition. | `when: not ansible_distribution == "Ubuntu"` |
| `in` | Membership operator. Checks if a value exists in a sequence. | `when: "nginx" in installed_packages` |
| `not in` | Membership operator. Checks if a value does not exist in a sequence. | `when: "nginx" not in installed_packages` |
| `is defined` | Existence check. Ensures a variable is defined. | `when: some_var is defined` |
| `is not defined` | Existence check. Ensures a variable is not defined. | `when: some_var is not defined` |
| `is truthy` | Checks if a variable evaluates to true (non-empty, non-zero). | `when: some_var is truthy` |

Condition 1: Using in
Let’s dive into some other conditions and their use cases! One common use of when is to act as a safety net, ensuring tasks don’t run unless the right conditions are met. For example, imagine you have a variable called installed_packages that lists all the packages currently installed. If this list doesn’t include a super-important package, we’ll want to add it—but only if it’s missing! You can use when to check for that package (like sl) before running the task to install it.

student@bchd:~$ vim ~/mycode/when-in.yml

---
- name: Install only if not in the package list
  hosts: planetexpress
  gather_facts: yes

  vars:
    installed_packages:
      - apache2
      - mysql

  tasks:
    - name: Ensure sl is installed
      ansible.builtin.apt:
        name: sl
        state: present
      become: yes
      when: "'sl' not in installed_packages"

Run the playbook:

student@bchd:~$ ansible-playbook ~/mycode/when-in.yml

Condition 2: Using is defined
The is defined condition checks if a variable is defined, or that variable has a value. Variables may be dynamically created during plays, but they may fail to define correctly. We can set a "safety net" by checking if the variable backup_path is valid BEFORE we try (and fail) to make a directory with it.

student@bchd:~$ vim ~/mycode/when-is-defined.yml

---
- name: Dynamically define backup path
  hosts: localhost
  gather_facts: yes

  tasks:
    - name: Set backup path if production server
      set_fact:
        backup_path: "{{ '/var/backups' if ansible_hostname == 'prod-server' else '' }}"
        # TRANSLATION: "If the server's hostname is 'prod-server,' set the
        # backup path to /var/backups; otherwise, leave it empty."

    - name: Create backup directory if path is valid
      file:
        path: "{{ backup_path }}"
        state: directory
      when: backup_path is defined and backup_path != ""
Run the playbook:

student@bchd:~$ ansible-playbook ~/mycode/when-is-defined.yml

Expected Result: The name of our host is NOT "prod-server," so backup_path is set as an empty string (''). Therefore, backup_path is NOT defined!

Condition 3: Using is truthy
is truthy is a condition that checks if a value is actually a boolean. This could be a really important condition, because YAML can be tricky with this- see the list below.

Things That Are Booleans in YAML
true (case-insensitive, so True or TRUE also work)
false (case-insensitive, so False or FALSE also work)
yes (case-insensitive, so Yes or YES also work) – interpreted as true
no (case-insensitive, so No or NO also work) – interpreted as false
on – interpreted as true
off – interpreted as false
Things That You’d Think Are Booleans But Actually Aren’t
"true" (as a string, wrapped in quotes, it’s treated as a string, not a Boolean)
"false" (same as above, treated as a string)
"yes" (quoted, it’s a string, not a Boolean)
"no" (quoted, it’s a string, not a Boolean)
"on" (quoted, treated as a string)
"off" (quoted, treated as a string)
0 or 1 (numerical values, not Booleans, though they are often confused as such)
Any non-empty string (e.g., "enabled", "disabled") – always treated as a string
Quick Tip: To avoid confusion, always use true or false without quotes if you mean Booleans. Quoted versions ("true", "false") will always be treated as strings.
With that in mind, let's write a playbook that will skip a task unless a feature flag is explicitly enabled.

student@bchd:~$ vim ~/mycode/when-is-truthy.yml

---
- name: Check for truthy flag
  hosts: localhost
  gather_facts: no

  vars:
    enable_feature_flag: true

  tasks:
    - name: Execute feature task
      debug:
        msg: "Feature is enabled!"
      when: enable_feature_flag is truthy
Run the playbook, it should work as written!

student@bchd:~$ ansible-playbook ~/mycode/when-is-truthy.yml

Expected Result: Ansible treats yes as a string, not a Boolean. Fix it by passing true instead.

But now, let's run the playbook with something that LOOKS like a boolean (but isn't) for enable_feature_flag:

student@bchd:~$ ansible-playbook ~/mycode/when-is-truthy.yml -e "enable_feature_flag=yes"

Expected Result: Ansible treats yes as a string, not a Boolean. Fix it by passing true instead.
